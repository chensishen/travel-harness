# 上轮失败原因分析与修复（2026-11-06）

## 已确认的程序问题

1. **文化介绍遗漏官方参观资料补查**。最终质量检查对旅行攻略和文化介绍均要求门票、开放时间、预约核实比例至少75%，但Verifier仅对travel_guide调用`enrich(..., search_missing=True)`。文化介绍未触发定向搜索，直到Assembler才因资料不足停止。现两类任务均启用现有的有限官方补查；未降低证据级别或75%要求。原有一个测试把文化介绍不补查当成预期，已按PRD修正，并新增经过真实Verifier与enrich调用链的回归。新测试先失败（queries为空），修复后取得四字段与官方核验链接。
2. **旧核验断点错误复用**。enrichment-progress签名此前未区分是否启用补查，旧的“不搜索”结果会跳过新补查。签名现包含search_missing；上述回归先写入旧模式断点，再运行实际Verifier，证明新模式不会被旧结果屏蔽。
3. **研究中断后重复已完成查询**。Researcher只在全部查询成功后保存阶段结果；后半段上游失败后，重试会再次调用已完成查询和模型。现按查询原有顺序原子保存research-progress，重试仅继续未完成查询。签名包含spec、查询列表和初始来源，条件改变时重新研究。回归先复现q1被调用两次，修复后只调用一次，保留来源编号及顺序；改变查询后旧断点失效。既有并发上限和兄弟任务取消行为保持通过。

4. **同一故障站点占满抓取预算**。实测苏州市园林局robots.txt连续302跳转至本站根地址，六次后仍不能读取。原候选选择在同等级来源中只按原始顺序取前3页，容易全部落到同一站点。现按来源等级优先，在同等级内轮流覆盖不同主机；仍每轮最多3页，L1始终先于L2/L3，保留原有robots和公开URL检查。定向回归先失败，修复后前三页分别覆盖三个官方主机。核验策略签名更新，使旧策略断点不会阻止重新补查。

5. **robots不可用与禁止抓取混淆**。实际官方站点robots超过5次同站重定向后仍不可读，旧代码直接阻止正文读取。依据[RFC 9309 §2.3.1.2–1.4](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.3.1.2)，只将重定向超过5次的robots视为不可用，允许尝试公开正文；真实Disallow、服务器错误、非公网地址与跨主机重定向仍阻止抓取。普通正文的重定向循环仍会报错。回归先复现失败后通过，并覆盖明确禁止与503不访问正文。实际同一苏州市园林局票价页重测17.37秒获取515字符正文，保留原网址及日期，不使用搜索摘要冒充正文。策略签名再更新，重新核验此前缺少官方材料的景点。

修改范围：backend/harness/graph.py、backend/harness/enrichment.py、backend/tools/sources.py、backend/tools/fetch.py，以及对应的source_recovery、performance、browser_repairs测试。
